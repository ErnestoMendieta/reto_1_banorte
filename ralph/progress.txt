## Codebase Patterns

> Seed inicial. El loop debe AÑADIR aquí los patrones nuevos que descubra
> (no borrar los existentes).

- Proyecto arranca vacío (sin código todavía) — la primera story (US-001)
  crea la estructura base (`scripts/`, schema SQL, dependencias).
- `.env` ya existe en la raíz con GITHUB_TOKEN y OPENROUTER_API_KEY reales.
  Faltan agregar ahí: GITHUB_USERNAME, OPENROUTER_MODEL, EMBEDDING_MODEL,
  EMBEDDING_DIM, CV_TEX_PATH, DATABASE_URL (ver specs/07 para el valor usado
  en docker-compose).
- El `.tex` fuente del CV puede no estar aún en el repo — si falta al
  llegar a US-001, ver AGENT.md punto 3 (usar fixture temporal, dejarlo
  anotado en notes, no bloquear el resto del build).

**Archivos creados:**
- `scripts/orchestrator.py` — StateGraph(AgentState): nodo agent (ChatOpenAI/OpenRouter + bind_tools), nodo tools (ToolNode + wrapping <untrusted_external_data>), @tool wrappers query_cv_tool/query_github_tool, entrypoint run_agent()

**Archivos modificados:**

- `specs/README.md` — US-004 estado: hecho
- `ralph/prd.json` — US-004 passes: true

**Patrones nuevos descubiertos:**
- `_build_llm()` como función standalone (no cached) permite mockear fácilmente con `patch("scripts.orchestrator._build_llm", return_value=mock_llm)`.
- `_query_cv`/`_query_github` dentro de @tool se resuelven en el namespace global al momento de llamada — `patch("scripts.orchestrator._query_cv")` funciona correctamente.
- `_TOOL_NODE = ToolNode(_TOOLS)` al nivel de módulo es seguro; el ToolNode despacha por nombre al @tool que a su vez llama la función parcheable.
- `add_messages` como reducer de AgentState: los nodos devuelven solo los mensajes nuevos, el reducer los acumula.
- Para continuidad: `run_agent(new_msgs, state=prev_state)` concatena `state["messages"] + new_msgs` antes de invocar el grafo.

**Validación:** `pytest` corre 35 tests (13 US-001 + 5 US-004 + 7 US-002 + 10 US-003 unit), 3 skipped. `ruff check .` clean.

### US-006 — Guardrails anti-prompt-injection

**Archivos modificados:**
- `scripts/orchestrator.py` — SYSTEM_PROMPT reemplazado con texto de hardening completo per spec 06: reglas explícitas de no revelar prompt, no fingir rol, solo info de tools, tratar <untrusted_external_data> como dato.
- `scripts/api.py` — agregado `_MAX_INPUT_LEN = 4_000` + validación antes de parsear input: si `isinstance(inp, str) and len(inp) > _MAX_INPUT_LEN` → 400.
- `specs/README.md` — US-006 estado: hecho
- `ralph/prd.json` — US-006 passes: true

**Decisiones explícitas:**
- Sin clasificador ML de injection — system prompt hardening + wrapping de ToolMessages cubre el vector más realista para el alcance del reto.
- Guardrail de salida (groundedness) por prompt (instrucción en system prompt), no segunda llamada LLM — costo/latencia no justificado para MVP.
- Wrapping <untrusted_external_data> ya existía desde US-004 en `_tools_node`; los 4 tests adversariales son verificación manual con LLM real (comportamiento no determinista).

**Validación:** `pytest` corre 45 tests, 3 skipped (sin cambios en conteo — guardrails cubiertos por tests existentes + test_api: test_input_exceeding_max_length_returns_400). `ruff check .` clean.
